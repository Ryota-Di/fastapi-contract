# Release notes — current contract checks

This release adds four complementary checks for FastAPI runtime contracts that
ordinary OpenAPI key/schema differences do not fully describe:

- Effective projected top-level response wire-key loss, including route alias policy.
- Supported top-level JSON BaseModel input binding-key loss.
- Hidden Query/Header/Cookie binding loss.
- Existing hidden parameter optional-to-required changes.

Confirmed losses report consumer wire identities. Relevant uncertainty identifies
the affected candidate or bounded region and its blocker. Independent BREAKING and
REVIEW findings remain visible together. SAFE means no incompatibility detected
in the supported contract surface, not full API compatibility.

## Baselines and upgrading

Schema v2 is now the snapshot default, with explicit response, body binding, and
parameter facts on every route. It has one public representation, without a
`fact_profile` field. Unpublished development snapshots with incomplete fact
families or profile metadata must be regenerated.

Existing schema-v1 baselines still decode and use the legacy extractor, checker,
and FAPI001 reporting. Each valid v1 check emits a non-failing stderr notice that
it is running legacy checks only. Legacy limitations and relevant REVIEW results
remain unchanged. Current facts are never inferred from v1 snapshots.

To enable current checks, regenerate from the accepted application revision in
its matching environment, then review and commit the new baseline:

```bash
fastapi-contract snapshot app.main:app -o fastapi-contract-baseline.json
```

This creates a new accepted baseline; it does not recover historical facts.
There is no automatic migration or `migrate` command. Explicit schema-v1 snapshot
creation remains available with `--schema-version 1`.

## Support and CI behavior

Supported versions are **Python 3.11+**, **FastAPI 0.141.1**, and **Pydantic 2.13.5**.
Starlette follows FastAPI's dependency. Keep the recorded Python/framework versions
identical when generating and checking a baseline. CI verifies Python 3.11 and 3.12.

Exit codes remain SAFE=0, BREAKING=1, REVIEW=1, ERROR=2. Compatibility results use
stdout; ERROR and v1 migration notices use stderr. Invalid baselines are rejected
before importing the target application. Output is deterministic and wire names
use JSON string escaping. Current checks use descriptive owner names; legacy
FAPI001 numbering is preserved without assigning new FAPI numbers.

## Known limitations

Conditional response omission, nested projection, full AliasChoices/AliasPath,
request coercion/strictness/constraints, missing Content-Type, route/slash behavior,
hidden operation availability, Path parameter checks and new required parameter
additions remain outside scope. Arbitrary serializer/dependency/user-code behavior
is not analyzed. Relevant unsupported structures can produce scoped REVIEW.
OpenAPI diff remains necessary for ordinary documented schema changes.
